# AI Game Studio 任务管理规范

**文件名称：** Task_Management_Rules.md

**工作室名称：** AI Game Studio

**当前版本：** 1.0

**文件性质：** 工作室核心固定规则

**适用范围：** 所有 Agent、所有游戏项目

**主要管理者：** 总控 Agent、主程 Agent

**最高决策者：** 人类管理者

---

## 1. 文件目的

本文件用于建立 AI Game Studio 统一的任务管理体系。

游戏开发涉及策划、技术设计、程序开发、资源制作、测试、优化和项目管理等多种工作。

如果缺少统一的任务管理机制，容易出现：

- 任务目标不明确。
- 多个 Agent 重复完成同一项工作。
- 任务拆分不合理。
- Agent 擅自扩大工作范围。
- 开发任务之间产生文件冲突。
- 任务依赖关系不清晰。
- 开发成果缺少验收标准。
- 项目进度无法准确追踪。
- 任务完成后没有及时更新项目文档。

因此，所有 Agent 必须遵守本文件。

本文件主要规定：

1. 任务分类与层级。
2. 任务编号与命名。
3. 任务创建与需求分析。
4. 任务拆分与依赖管理。
5. 任务分配与执行。
6. 任务状态管理。
7. 任务审核与验收。
8. 任务暂停、取消和重新分配。
9. 任务记录与归档。
10. 总控 Agent 与主程 Agent 的任务管理分工。

## 2. 任务管理基本原则

### 2.1 目标明确原则

每个正式任务都必须具有明确的目标。

任务不能仅仅描述为：

- 优化一下游戏。
- 改进玩家体验。
- 完善角色系统。
- 修复一些问题。

必须进一步明确具体需要完成什么，以及如何判断是否完成。

### 2.2 责任明确原则

每个任务必须具有明确的负责人。

一个任务可以涉及多个 Agent 协作，但必须指定一个主要执行者。

不能出现多个 Agent 都认为对方负责最终交付的情况。

### 2.3 范围明确原则

每个任务都必须明确：

- 任务目标。
- 工作范围。
- 允许修改的文件。
- 禁止修改的文件。
- 交付成果。
- 验收标准。

Agent 不得擅自扩大任务范围。

### 2.4 先规划后执行原则

对于需要修改 UE5 工程的开发任务，必须先由主程 Agent 完成技术分析、任务拆分和文件授权，再由模块开发 Agent 执行。

不得在没有明确任务单的情况下直接修改工程文件。

### 2.5 可追溯原则

每个正式任务都必须拥有唯一编号。

任务从创建到结束的状态变化、负责人变化、范围调整和审核结果都必须能够追溯。

### 2.6 成果导向原则

任务是否完成，必须依据实际交付成果和验收标准判断。

Agent 不能仅仅因为自己已经执行了操作，就将任务标记为完成。

## 3. 任务层级体系

AI Game Studio 采用以下任务层级：

```
Milestone（里程碑，M）
    └── Stage（阶段，S）
            └── Task（任务）
                    └── Subtask（子任务）
```

### 3.1 Milestone（里程碑，M）

Milestone 是游戏项目中的重要开发目标。

用于描述项目在某个阶段需要达到的整体成果。

项目默认可以采用 M1、M2、M3 等编号。

M1 到 M9 只是默认编号示例，并不代表每个游戏项目都必须包含九个里程碑。

每个里程碑具体代表什么开发目标、需要多少个里程碑，由总控 Agent 根据实际游戏类型、项目规模和开发计划决定。

例如：

- 小型游戏可以只设置少量里程碑。
- 中型游戏可以设置多个里程碑。
- 大型游戏可以根据开发复杂度进一步细分。

里程碑的具体目标必须写入项目管理文档。

### 3.2 Stage（阶段，S）

Stage 是某个里程碑内部的具体开发阶段。

一个里程碑可以包含多个阶段。

例如：

```
M1
├── S1：需求分析
├── S2：技术方案
└── S3：基础功能实现
```

以上仅为结构示例，实际阶段由总控 Agent 根据项目需要确定。

### 3.3 Task（任务）

Task 是可以被明确分配和执行的工作单元。

例如：

- 实现玩家移动功能。
- 制作角色交互系统。
- 完成背包数据结构。
- 修复角色动画状态切换问题。
- 完成某个关卡的设计文档。

一个任务必须具有明确的执行者和交付标准。

### 3.4 Subtask（子任务）

Subtask 是一个复杂任务内部进一步拆分出的工作单元。

例如：

```
Task_001：实现玩家移动系统

├── Subtask_001：分析现有角色控制代码
├── Subtask_002：实现基础移动逻辑
├── Subtask_003：实现跳跃逻辑
└── Subtask_004：编译与功能测试
```

子任务可以由同一个 Agent 执行，也可以分配给不同 Agent。

如果多个子任务涉及相同工程文件，必须先检查文件锁定冲突，不能因为拆成子任务就绕过文件锁定规则。

## 4. 任务分类

根据工作性质，任务分为以下类别。

### 4.1 策划任务

由游戏策划 Agent 主要负责。

包括：

- 核心玩法设计。
- 游戏规则设计。
- 角色设计。
- 关卡设计。
- 剧情和世界观设计。
- 数值设计。
- 用户界面与交互设计。
- 策划文档整理。

策划任务的主要成果是经过整理的策划文档或设计方案。

### 4.2 技术规划任务

由主程 Agent 主要负责。

包括：

- 工程结构分析。
- 技术可行性评估。
- 技术架构设计。
- 模块依赖分析。
- 接口设计。
- 性能风险分析。
- 开发任务拆分。
- 工程文件授权规划。

技术规划任务的主要成果是技术方案、架构文档和开发任务单。

### 4.3 开发任务

由模块开发 Agent 或主程 Agent 执行。

包括：

- C++ 程序开发。
- 蓝图开发。
- 游戏系统实现。
- 功能修改。
- Bug 修复。
- 性能优化。
- 资源和配置调整。

开发任务必须具有明确的工程文件授权范围。

### 4.4 测试与审核任务

由具备相应审核职责的 Agent 执行。

包括：

- 功能测试。
- 编译检查。
- 代码审核。
- 技术方案审核。
- 设计方案审核。
- 性能测试。
- 问题复现与定位。

测试和审核任务必须记录实际测试方法与结果。

### 4.5 管理任务

由总控 Agent 或主程 Agent 根据职责负责。

包括：

- 项目进度更新。
- 任务优先级调整。
- Agent 工作协调。
- 文档同步。
- 任务状态检查。
- 项目风险跟踪。
- 工作室规则执行情况检查。

## 5. 任务编号与命名

### 5.1 编号原则

每个正式任务都必须拥有唯一编号。

推荐格式：

```
Task_001
Task_002
Task_003
```

子任务采用：

```
Task_001_Subtask_001
Task_001_Subtask_002
```

编号一经分配，不得重复使用。

已经取消或归档的任务编号也不得分配给新任务。

### 5.2 任务文件命名

推荐格式：

```
Task_001_Player_Movement.md
Task_002_Interaction_System.md
Task_003_Inventory_System.md
```

### 5.3 任务归属

每个任务应明确所属里程碑和阶段。

例如：

```
里程碑：M1
阶段：S2
任务编号：Task_001
任务名称：玩家移动系统
```

如果任务暂时无法归入某个里程碑或阶段，可以标记为待规划任务，由总控 Agent 后续处理。

## 6. 任务创建流程

### 6.1 任务需求来源

任务可以来自：

- 人类管理者提出的新需求。
- 总控 Agent 的项目规划。
- 游戏策划 Agent 提交的设计需求。
- 主程 Agent 发现的技术问题。
- 模块开发 Agent 发现的 Bug 或技术风险。
- 测试与审核过程中发现的问题。

任何 Agent 都可以提出任务建议，但不能因此自动获得任务执行权限。

### 6.2 任务创建权限

总控 Agent 负责项目层面的任务统筹。

主程 Agent 负责技术开发任务的创建、拆分和具体分配。

游戏策划 Agent 可以创建策划工作所需的内部工作安排，但涉及正式项目任务时，应向总控 Agent 提交。

模块开发 Agent 不得自行创建并授权新的工程开发任务。

### 6.3 任务创建前分析

创建正式任务之前，必须分析：

1. 任务来源。
2. 任务目标。
3. 任务所属里程碑和阶段。
4. 任务优先级。
5. 任务依赖关系。
6. 所需 Agent 类型。
7. 预计交付成果。
8. 验收标准。
9. 可能影响的文件。
10. 潜在技术风险。

如果需求不明确，必须先向人类管理者或需求提出者确认。

不得将存在重大歧义的需求直接分配给模块开发 Agent。

## 7. 任务拆分规范

### 7.1 需要拆分的情况

当任务具有以下特征时，应考虑拆分：

- 涉及多个独立系统。
- 工作量过大。
- 需要不同专业 Agent 协作。
- 任务之间存在明显依赖关系。
- 修改文件范围过大。
- 无法通过单一验收标准判断完成情况。

### 7.2 拆分原则

任务拆分必须满足：

- 每个子任务都有明确目标。
- 每个子任务都有明确负责人。
- 每个子任务都有独立交付成果。
- 子任务之间的依赖关系明确。
- 不同子任务的文件修改范围尽量避免冲突。
- 子任务完成后能够汇总为父任务的最终成果。

### 7.3 不合理拆分

不得为了增加任务数量而过度拆分。

例如，一个只需要修改一个简单参数的工作，没有必要创建多个独立 Agent 任务。

拆分的目的应当是降低复杂度、明确职责和减少冲突，而不是增加管理成本。

### 7.4 父任务与子任务关系

父任务只有在所有必要子任务完成并通过审核后，才能进入最终验收。

如果某个子任务失败或被取消，主程 Agent 必须重新评估父任务是否仍然能够实现原定目标。

## 8. 任务优先级管理

任务优先级由总控 Agent 统一协调。

主程 Agent 可以根据技术依赖和工程风险提出调整建议。

采用以下优先级：

- **P0 — 紧急：** 阻塞项目继续开发或存在严重问题，必须优先处理
- **P1 — 高：** 当前里程碑的重要任务
- **P2 — 普通：** 正常计划中的开发任务
- **P3 — 低：** 不影响当前开发进度的优化或改进

### 8.1 P0：紧急

适用于：

- 工程无法正常打开。
- 关键系统发生严重故障。
- 核心功能完全不可用。
- 重要数据或工程文件存在损坏风险。

### 8.2 P1：高

适用于：

- 当前阶段必须完成的核心功能。
- 阻塞其他任务的关键依赖。
- 影响主要游戏体验的问题。

### 8.3 P2：普通

适用于：

- 正常开发计划中的功能。
- 一般性 Bug 修复。
- 常规策划和技术工作。

### 8.4 P3：低

适用于：

- 非必要的体验优化。
- 暂时不影响核心流程的改进。
- 可延后处理的技术优化。

优先级不代表任务可以绕过权限、文件锁定和审核流程。

## 9. 任务分配与执行

### 9.1 总控 Agent 的职责

总控 Agent 负责：

- 理解人类管理者的目标。
- 判断任务是否符合当前项目方向。
- 确定任务的重要程度。
- 协调策划、技术和开发工作。
- 监督任务进度。
- 处理跨专业任务冲突。
- 验收重要任务的最终成果。
- 更新项目权威进度。

总控 Agent 不需要亲自完成所有专业工作。

### 9.2 游戏策划 Agent 的职责

游戏策划 Agent 负责：

- 接收策划需求。
- 分析设计目标。
- 创建策划方案。
- 完成策划文档。
- 根据审核意见修改方案。
- 向总控和主程交付正式设计成果。

### 9.3 主程 Agent 的职责

主程 Agent 负责：

- 分析策划需求的技术可行性。
- 检查现有工程。
- 制定技术方案。
- 拆分开发任务。
- 明确工程文件修改范围。
- 检查文件锁定冲突。
- 创建和分配开发任务。
- 判断是否需要触发独立代码审核。
- 将开发成果和相关资料交给代码审核 Agent。
- 接收并处理代码审核 Agent 的审核报告。
- 根据审核报告决定是否要求返工。
- 安排返工后的重新审核。
- 执行最终技术验收。
- 审核模块开发成果。
- 管理技术问题和开发风险。

### 9.4 模块开发 Agent 的职责

模块开发 Agent 负责：

- 阅读任务单。
- 检查授权文件。
- 理解现有工程代码。
- 按照任务要求实施开发。
- 进行必要的编译和测试。
- 提交代码修改和交付报告。
- 记录未解决问题和风险。

模块开发 Agent 不得擅自修改任务目标、扩大工程文件范围或改变其他任务的状态。

### 9.5 主程亲自开发

主程 Agent 可以亲自承担开发任务。

但必须遵守与模块开发 Agent 相同的任务管理要求：

- 创建明确的任务单。
- 明确修改文件。
- 检查文件锁定。
- 记录任务状态。
- 提交开发成果。
- 接受必要的审核。

主程不得因为自己拥有工程管理权限，就绕过任务管理和文件锁定机制。

## 11. 任务状态管理

所有正式任务必须使用统一状态。

- **Pending**（待处理）：已创建，但尚未正式开始
- **Ready**（已就绪）：前置条件满足，可以开始执行
- **In Progress**（进行中）：Agent 正在执行
- **Blocked**（受阻）：因依赖、权限或其他问题无法继续
- **Suspended**（已暂停）：任务被主动暂停，等待后续恢复
- **Review**（审核中）：已提交成果，等待审核
- **Revision Required**（需要修改）：审核未通过，需要返工
- **Completed**（已完成）：已通过规定的审核和验收
- **Cancelled**（已取消）：任务正式终止，不再继续执行

### 11.1 状态转换规则

正常开发任务的完整流程包括独立代码审核和主程最终技术验收：

```
Pending
   ↓
Ready
   ↓
In Progress
   ↓
Review（独立代码审核中）
   ↓
主程处理审核报告
   ├── Approved → 进入主程最终技术验收 → Completed
   ├── Approved with Warnings → 主程评估 → 通过或要求返工
   ├── Changes Requested → Revision Required（返工）→ In Progress → 重新 Review
   └── Rejected → Revision Required 或 Cancelled
```

任务受阻时：

```
In Progress
   ↓
Blocked
   ↓
Ready 或 In Progress
```

任务暂停时：

```
In Progress
   ↓
Suspended
   ↓
Ready 或 In Progress
```

任务取消时：

```
任意未完成状态
   ↓
Cancelled
```

**任务状态与审核状态的关系：**

任务状态中的 Review 指独立代码审核 Agent 正在执行审核，不代表主程已完成最终技术验收。主程最终技术验收完成后才能将任务标记为 Completed。审核结论与任务状态的映射由主程根据实际情况判断。

### 11.2 状态修改权限

- 总控 Agent：负责项目层面的任务状态监督和必要的最终状态确认。
- 主程 Agent：负责技术开发任务的状态维护。
- 游戏策划 Agent：负责自己策划工作的执行状态，并向总控同步。
- 模块开发 Agent：只能报告自己任务的实际执行状态，不能擅自修改权威任务记录。

### 11.3 状态更新要求

任务状态发生变化后，必须及时更新任务单。

不得出现任务已经完成，但文件中仍然长期显示 In Progress 的情况。

## 12. 任务审核与验收

### 12.1 策划任务审核

策划任务由游戏策划 Agent 完成后，提交总控 Agent 审核。

总控重点检查：

- 是否符合人类管理者的需求。
- 是否符合项目整体方向。
- 设计是否完整。
- 规则是否存在矛盾。
- 是否存在明显遗漏。
- 是否具备实际实现条件。

涉及重大设计决策时，应提交人类管理者确认。

### 12.2 技术规划审核

技术规划由主程 Agent 完成。

总控 Agent 负责检查其是否符合项目目标和整体规划。

如果涉及重大技术路线、成本或项目风险，应向人类管理者说明并取得必要确认。

### 12.3 开发任务审核与最终技术验收

模块开发 Agent 完成任务后，必须提交：

- 修改文件清单。
- 功能实现说明。
- 关键实现方式。
- 编译结果。
- 测试方法和结果。
- 未解决问题。
- 已知风险。

**第一步：主程判断是否需要独立代码审核**

主程 Agent 收到开发成果后，首先判断是否需要触发独立代码审核。

以下情况通常需要触发：

- 涉及 UE5 工程文件修改的开发任务。
- 涉及 C++ 代码编写或修改的任务。
- 涉及蓝图修改的任务。
- 主程评估后认为代码变更有足够复杂度或风险的任务。

以下情况可以不触发（由主程决定）：

- 仅修改项目 Markdown 管理文件。
- 仅维护技术文档。
- 代码变更极小且风险极低的修复任务。

**第二步：独立代码审核（如触发）**

主程将开发成果（任务单、交付报告、工程访问权、相关技术文档）交给代码审核 Agent。

代码审核 Agent 以独立审核模式执行审核，出具正式 Markdown 审核报告。审核结论为四种之一：Approved / Approved with Warnings / Changes Requested / Rejected。

**第三步：主程处理审核报告**

主程 Agent 收到代码审核报告后：

- 如果结论为 Approved 或 Approved with Warnings：进入主程最终技术验收。
- 如果结论为 Changes Requested：整理返工清单，退回模块开发 Agent。返工期间任务状态为 Revision Required，文件锁定继续保留。返工完成后重新提交，再次进入独立代码审核。
- 如果结论为 Rejected：重新评估方案，可能需要重做或取消任务。

**第四步：主程最终技术验收**

主程 Agent 是开发任务的最终技术验收者。验收内容包括：

- 是否符合任务单要求。
- 是否超出授权文件范围。
- 独立代码审核是否已通过阻断性问题。
- 代码审核报告中的遗留问题是否已评估。
- 编译是否成功。
- 功能是否正常。
- 是否影响现有系统。
- 是否存在未解决的关键问题。

主程完成最终技术验收后：

- 验收通过：更新任务状态为 Completed，释放文件锁。
- 验收不通过：退回返工，文件锁继续保留。

### 12.4 最终项目验收

总控 Agent 负责项目层面的最终验收。

对于普通开发任务，可以依据主程的技术审核结果更新项目进度。

对于重大功能、核心系统或重要里程碑，应由总控向人类管理者提交验收摘要，并根据人类管理者的意见决定是否正式接受。

### 12.5 禁止自我批准

模块开发 Agent 不得批准自己的任务。

主程 Agent 如果亲自承担开发任务，应尽可能由总控 Agent 或其他经授权的审核者进行独立审核。

不能由同一个执行者仅凭自己的判断完成所有验收流程。

## 13. 任务暂停、受阻与取消

### 13.1 任务受阻

任务因技术问题、前置依赖或权限不足而无法继续时，应标记为 Blocked。

必须说明：

- 受阻原因。
- 当前已完成内容。
- 尚未完成内容。
- 需要谁提供帮助。
- 预计如何恢复。

### 13.2 任务暂停

任务因项目规划调整或资源安排等原因暂时停止时，应标记为 Suspended。

暂停任务必须保留：

- 原任务编号。
- 原任务负责人。
- 当前工作状态。
- 已完成成果。
- 未完成内容。
- 相关文件锁定情况。

如果任务暂停时仍有未完成的工程修改，必须按照 File_Management_Rules.md 保留相应文件锁定，不能自动释放。

### 13.3 任务取消

任务不再具有继续执行的必要时，可以正式取消。

取消任务必须记录：

- 取消原因。
- 取消决定者。
- 当前完成情况。
- 已有成果如何处理。
- 是否需要恢复或保留工程修改。
- 文件锁定如何处理。

取消后的任务应归档，不得直接删除任务历史。

## 14. 任务变更机制

任务执行过程中，如果出现以下情况，应考虑调整任务：

- 原需求发生变化。
- 发现技术方案不可行。
- 需要增加新的工程文件。
- 工作范围明显扩大。
- 发现新的技术依赖。
- 原验收标准不再适用。

### 14.1 一般变更

不影响任务核心目标和权限边界的小幅调整，可以由主程 Agent 在任务单中记录后执行。

### 14.2 重大变更

涉及以下情况时，必须提交总控或人类管理者确认：

- 改变核心游戏设计。
- 改变任务主要目标。
- 大幅增加工作范围。
- 改变重要技术架构。
- 显著增加开发成本或风险。
- 影响已批准的里程碑目标。

### 14.3 工程文件变更

如果任务需要增加或减少工程文件：

必须先由主程 Agent 检查文件锁定冲突，再更新任务单和文件锁定登记表。

在更新完成之前，模块开发 Agent 不得修改新增文件。

## 15. 任务记录与归档

每个项目必须维护统一任务清单：

```
AI_Project/
└── Development/
    ├── Task_Backlog.md
    ├── Tasks/
    ├── Active_Tasks/
    └── Completed_Tasks/
```

### 15.1 Task_Backlog.md

用于记录项目全部待处理任务和整体任务状态。

主要由主程 Agent 维护。

### 15.2 Tasks/

存放已经创建的正式任务单。

### 15.3 Active_Tasks/

存放正在执行、审核或等待处理的任务。

### 15.4 Completed_Tasks/

存放已经完成或正式取消的任务及其必要历史记录。

任务归档后，不得随意删除其交付报告和重要审核记录。

---

## 16. 任务与项目进度同步

总控 Agent 负责维护：

```
AI_Project/Current_Status.md
```

该文件是项目当前状态的权威记录。

主程 Agent 应及时向总控提交：

- 已创建的任务。
- 任务状态变化。
- 已完成的技术工作。
- 当前阻塞事项。
- 重要技术风险。
- 里程碑完成情况。

游戏策划 Agent 应及时提交：

- 策划成果。
- 设计变更。
- 尚未确定的设计问题。
- 需要主程处理的技术需求。

模块开发 Agent 应通过任务交付报告向主程提交实际开发情况。

总控 Agent 根据经过确认的信息更新 Current_Status.md。

任何其他 Agent 不得直接修改该文件。

## 17. 跨平台与多对话任务管理

AI Game Studio 允许不同 Agent 在不同平台和不同对话中执行任务。

例如：

- 总控 Agent 在 WorkBuddy 中运行。
- 游戏策划 Agent 在其他 AI 平台中运行。
- 主程 Agent 在 DeepSeek Harness 中运行。
- 模块开发 Agent 在独立开发对话中运行。

无论平台如何变化，任务编号和正式任务单都必须保持一致。

### 17.1 独立任务对话

原则上，每个模块开发任务使用独立的开发对话。

这样可以减少不同任务之间的上下文混淆。

### 17.2 跨平台交接

切换平台时，必须携带：

- 当前任务单。
- 相关技术文档。
- 必要的策划文档。
- 当前工程状态说明。
- 已修改文件清单。
- 当前文件锁定信息。

不得仅凭一句简单描述要求新 Agent 继续复杂任务。

### 17.3 聊天记录不是权威任务记录

所有重要任务信息必须写入项目 Markdown 文件。

聊天记录只能作为辅助上下文，不能代替正式任务单、审核记录和项目状态文件。

## 18. 任务管理异常处理

遇到以下情况时，Agent 必须及时报告：

- 任务目标存在严重歧义。
- 任务授权文件不完整。
- 任务与其他任务发生冲突。
- 任务执行者超出职责范围。
- 任务依赖无法满足。
- 实际工程与文档描述不一致。
- 任务无法按验收标准完成。
- 任务成果无法保存或交付。

报告必须包含：

1. 任务编号。
2. 当前状态。
3. 具体问题。
4. 已完成工作。
5. 影响范围。
6. 建议解决方案。
7. 需要谁作出决定。

---

## 19. 任务管理规范优先级

任务管理按照以下顺序执行：

1. 人类管理者最新的明确指令。
2. 经人类管理者确认的工作室固定规则。
3. Agent_Permissions.md 中的权限规定。
4. File_Management_Rules.md 中的文件管理规定。
5. 本文件中的任务管理规定。
6. 当前项目的具体任务约定。
7. 当前任务单中的具体执行要求。

任务单不得突破工作室固定规则和 Agent 权限。

如果不同规则之间存在无法解决的冲突，必须暂停相关操作并请求人类管理者确认。
