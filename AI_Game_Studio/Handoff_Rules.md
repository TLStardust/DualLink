# AI Game Studio Agent 交接规范

**文件名称：** Handoff_Rules.md

**工作室名称：** AI Game Studio

**当前版本：** 1.0

**文件性质：** 工作室核心固定规则

**适用范围：** 所有 Agent、所有游戏项目

**主要管理者：** 总控 Agent

**技术交接管理者：** 主程 Agent

**最高管理者：** 人类管理者

---

## 1. 文件目的

本文件用于建立 AI Game Studio 统一的工作交接机制。

游戏开发过程中，不同 Agent 可能需要：

- 将策划成果交给主程 Agent。
- 将技术方案交给模块开发 Agent。
- 将开发成果交给主程 Agent 审核。
- 将审核结果交给总控 Agent。
- 将任务从一个模块开发 Agent 转交给另一个模块开发 Agent。
- 在不同 AI 平台之间切换。
- 在不同模型或独立对话之间切换。
- 在任务中断后恢复之前的工作。

如果缺少统一的交接规范，可能出现：

- 接收方不知道任务的真实目标。
- 已经完成的工作被重复执行。
- 重要技术决策丢失。
- Agent 不清楚当前工程状态。
- 新 Agent 错误理解旧 Agent 的工作成果。
- 任务文件和聊天记录内容不一致。
- 原任务的文件锁定状态被错误释放。
- Agent 更换后擅自扩大工作范围。

因此，所有 Agent 必须遵守本文件。

本文件主要规定：

1. 交接基本原则。
2. Agent 之间的交接关系。
3. 交接文件的存储方式。
4. 标准交接报告格式。
5. 不同工作类型的交接要求。
6. 跨平台和跨模型交接。
7. 任务中断与接手。
8. 交接审核与确认。
9. 交接异常处理。

## 2. 交接基本原则

### 2.1 正式文件优先原则

所有具有长期价值的工作成果必须保存在对应的项目 Markdown 文件中。

交接时应优先使用正式项目文件，而不是仅依靠聊天记录。

聊天记录可以提供额外背景，但不能代替正式策划文档、技术文档、任务单和交付报告。

### 2.2 信息完整原则

交接方必须提供接收方继续工作所需要的信息。

至少应说明：

- 为什么进行交接。
- 当前需要完成什么。
- 已经完成什么。
- 还有什么没有完成。
- 当前有哪些已知问题。
- 接收方可以操作哪些文件。
- 哪些事项需要特别注意。

### 2.3 权限继承原则

接收方只能继承原任务中已经明确授权的权限。

交接不等于自动扩大权限。

如果接收方需要修改新的文件，必须先由主程 Agent 检查并更新任务授权和文件锁定记录。

### 2.4 状态一致原则

交接报告、任务单、文件锁定登记表和项目状态必须保持一致。

如果这些记录存在冲突，必须先核实真实状态，再继续执行。

### 2.5 可追溯原则

每次正式交接都应能够追溯：

- 交接方。
- 接收方。
- 交接时间。
- 交接原因。
- 交接任务。
- 交接内容。
- 接收方确认结果。

### 2.6 人工交接原则

当前工作室采用人工交接机制。

总控 Agent、策划 Agent、主程 Agent 和模块开发 Agent 不得假设自己能够直接调用其他 Agent。

需要跨 Agent 协作时，由人类管理者复制相关任务单、文档或交接报告，发送给目标 Agent。

如果未来某个平台支持自动 Agent 通信，也必须遵守本文件的权限和交接规则。

## 3. 交接类型

### 3.1 策划成果交接

游戏策划 Agent 将已经完成的设计成果交给总控 Agent 或主程 Agent。

例如：

- 核心玩法设计。
- 角色设计。
- 关卡设计。
- 游戏规则。
- UI/UX 设计。
- 数值设计。

交接重点：

- 设计目标。
- 设计内容。
- 核心规则。
- 尚未确定的问题。
- 需要技术评估的内容。

### 3.2 技术方案交接

主程 Agent 将技术方案和开发任务交给模块开发 Agent。

例如：

- 技术架构。
- 模块职责。
- 接口定义。
- 依赖关系。
- 工程文件授权。
- 开发任务单。

交接重点：

- 任务目标。
- 具体实现要求。
- 现有工程结构。
- 允许修改的文件。
- 禁止修改的文件。
- 技术限制。
- 验收标准。

### 3.3 开发成果交接

模块开发 Agent 将开发成果交给主程 Agent。

交接重点：

- 实际完成的功能。
- 修改过的文件。
- 关键实现方式。
- 编译结果。
- 测试结果。
- 未解决问题。
- 已知风险。

### 3.4 开发成果至代码审核交接

主程 Agent 判断需要独立代码审核后，将开发成果交给代码审核 Agent。

这是本次架构新增的交接类型。

交接方：主程 Agent

接收方：代码审核 Agent

交接资料至少包含：

- 当前开发任务单完整内容。
- 模块开发 Agent 的完整交付报告。
- 相关技术架构文档（Technical_Architecture.md 等）。
- 模块依赖文档（Module_Dependencies.md）。
- 任务对应的技术方案说明（如有）。
- 工程文件访问权限（如可提供）。
- 当前 File_Lock_Register.md 中本任务的锁定信息。

交接重点：

- 代码审核 Agent 需要检查的文件范围。
- 需要对照的任务验收标准。
- 开发 Agent 报告的编译和测试结果。
- 需要特别关注的技术风险区域。

交接前提：主程已收到模块开发 Agent 提交的完整交付报告。

交接后：代码审核 Agent 进入独立审核模式，开始只读检查。

### 3.5 代码审核报告回传交接

代码审核 Agent 完成审核后，将审核报告回传给主程 Agent。

交接方：代码审核 Agent

接收方：主程 Agent

交接资料：

- 正式 Markdown 审核报告（存放于 Reviews/Code_Reviews/{任务编号}_Code_Review.md）。

交接重点：

- 审核结论（Approved / Approved with Warnings / Changes Requested / Rejected）。
- 问题列表和严重程度分级。
- 无法检查的内容及原因。
- 遗留风险。

交接后：主程根据审核报告决定后续处理（进入最终技术验收、整理返工清单、或重新评估方案）。

### 3.6 返工与重新审核交接

当代码审核结论为 Changes Requested 或 Rejected 时，涉及以下交接：

**主程至模块开发 Agent（返工指令）**

交接资料：

- 代码审核报告中的问题列表。
- 主程整理的返工清单（明确需要修复的问题、优先级、验收标准）。
- 原任务单和原技术方案。

交接重点：

- 具体需要修复的 Critical 和 High 级别问题。
- 返工期间文件锁定保持不变。
- 返工完成后需要重新提交交付报告并进入重新审核。

**模块开发 Agent 至主程（返工后重新提交）**

交接资料：

- 返工后的交付报告（说明修复了哪些问题、如何修复的、是否引入新问题）。
- 修改文件清单。
- 新的编译和测试结果。

**主程至代码审核 Agent（重新审核）**

交接资料：

- 原审核报告（引用）。
- 模块开发 Agent 返工后的交付报告。
- 本次返工修改的文件清单。
- 新的编译和测试结果。

交接重点：

- 上次审核指出的问题是否已修复。
- 修复过程中是否引入新问题。

### 3.7 技术审核交接

主程 Agent 完成最终技术验收后，将验收结果交给总控 Agent。

交接重点：

- 审核是否通过。
- 是否符合任务要求。
- 是否存在遗留问题。
- 是否影响其他系统。
- 是否可以进入下一阶段。

### 3.8 项目管理交接

总控 Agent 将项目状态、任务安排和后续计划交给其他 Agent。

交接重点：

- 项目当前进度。
- 当前里程碑和阶段。
- 已完成的重要成果。
- 当前进行中的任务。
- 当前阻塞事项。
- 下一步计划。
- 需要人类管理者决定的事项。

### 3.9 Agent 更换交接

当某项任务需要更换执行 Agent 时，由原执行者向新执行者交接当前工作。

例如：

- 更换模块开发 Agent。
- 从 WorkBuddy 切换到 DeepSeek Harness。
- 从云端模型切换到本地模型。
- 原对话上下文过长，需要创建新对话继续工作。

此类交接必须特别关注当前工程状态和文件锁定状态。

## 4. 交接文件存储规范

每个游戏项目必须拥有独立的交接目录：

```
AI_Project/
└── Handoffs/
    ├── Designer/
    ├── Programmer/
    └── Developer/
```

### 4.1 Designer/

用于存放游戏策划 Agent 的交接文件。

例如：

```
Designer/
├── Design_Handoff_001.md
└── Design_Handoff_002.md
```

### 4.2 Programmer/

用于存放主程 Agent 的技术交接文件。

例如：

```
Programmer/
├── Technical_Handoff_001.md
└── Technical_Handoff_002.md
```

### 4.3 Developer/

用于存放模块开发 Agent 的开发交付报告。

例如：

```
Developer/
├── Task_001_Developer_Report.md
├── Task_002_Developer_Report.md
└── Task_003_Developer_Report.md
```

### 4.4 文件命名要求

正式交接文件应使用能够识别交接类型和关联任务的名称。

如果交接涉及具体开发任务，必须包含任务编号。

同一任务发生多次交接时，应保留历史报告，不得直接覆盖旧报告。

推荐使用递增编号或版本号区分不同交接记录。

---

## 5. 通用交接报告模板

所有正式交接原则上应使用统一模板。

不同类型的交接可以增加专属字段，但不得省略核心信息。

```
# Agent 工作交接报告

## 1. 基本信息

- 交接编号：
- 关联任务编号：
- 交接类型：
- 交接方：
- 接收方：
- 交接日期：
- 交接原因：

## 2. 交接目标

说明本次交接希望接收方完成什么工作。

## 3. 当前工作背景

说明相关项目背景、需求来源和必要上下文。

## 4. 已完成工作

列出已经完成的工作及对应成果。

## 5. 当前未完成工作

列出尚未完成的工作。

## 6. 相关文件

列出接收方需要阅读的正式文件及其路径。

## 7. 当前文件状态

说明涉及的文件是否已经修改、保存和检查。

## 8. 当前权限范围

明确接收方可以读取、创建和修改哪些文件。

## 9. 文件锁定状态

说明当前任务涉及哪些锁定文件，以及锁定状态。

## 10. 已知问题与风险

列出尚未解决的问题和可能存在的风险。

## 11. 下一步工作建议

说明建议接收方首先执行什么工作。

## 12. 交接方声明

说明交接信息是否完整，是否存在尚未写入正式文件的内容。

## 13. 接收方确认

- 是否已阅读交接资料：
- 是否理解任务目标：
- 是否确认权限范围：
- 是否发现信息缺失：
- 是否接受交接：

## 14. 交接状态

- Pending：等待接收。
- Accepted：已接受。
- Rejected：拒绝接收。
- Completed：交接流程完成。
```

## 6. 策划成果交接规范

### 6.1 交接前要求

游戏策划 Agent 在交付设计成果之前，应确保：

- 设计目标明确。
- 核心规则完整。
- 关键机制之间没有明显矛盾。
- 已知问题得到标注。
- 设计文档已经保存。
- 文档中的术语符合 Terminology.md。

### 6.2 交接内容

策划成果交接至少包含：

1. 设计目标。
2. 设计背景。
3. 核心玩法或机制。
4. 具体规则。
5. 关键参数和数值。
6. 玩家体验目标。
7. 需要技术实现的功能。
8. 尚未确定的问题。
9. 相关策划文档路径。

### 6.3 总控审核

总控 Agent 收到策划成果后，应检查：

- 是否符合人类管理者的需求。
- 是否符合项目方向。
- 是否存在重大设计冲突。
- 是否有重要内容遗漏。
- 是否需要人类管理者确认。

通过审核后，才可以将设计成果作为正式的后续开发依据。

### 6.4 向主程交接

如果策划成果需要进入技术实现阶段，总控 Agent 应将已经确认的设计文档和必要说明交给主程 Agent。

主程 Agent 不得仅凭不完整的聊天摘要自行推测策划细节。

遇到设计歧义时，应向总控或策划 Agent 请求澄清。

## 7. 技术方案交接规范

### 7.1 交接前要求

主程 Agent 必须完成必要的工程检查和技术分析。

技术方案应与真实 UE5 工程保持一致。

不得仅根据策划文档推测当前工程结构。

### 7.2 交接内容

技术方案交接至少包含：

1. 需求来源。
2. 技术实现目标。
3. 当前工程结构。
4. 相关模块说明。
5. 模块依赖关系。
6. 接口和数据结构要求。
7. 具体开发任务。
8. 允许修改的文件。
9. 禁止修改的文件。
10. 编译与测试要求。
11. 验收标准。
12. 已知技术风险。

### 7.3 任务授权

主程 Agent 必须在任务单中明确开发权限。

模块开发 Agent 不能仅凭技术方案中的描述，自行推断可以修改哪些工程文件。

所有工程文件修改权限以正式任务单和文件锁定登记表为准。

### 7.4 接收方确认

模块开发 Agent 开始修改工程之前，必须确认：

- 已阅读任务单。
- 已理解技术要求。
- 已确认允许修改的文件。
- 已确认禁止修改的文件。
- 已理解验收标准。
- 已了解当前文件锁定情况。

如果任务单存在歧义，必须先向主程 Agent 提问。

## 8. 开发成果交接规范

### 8.1 交付前要求

模块开发 Agent 完成任务后，必须提交正式开发报告。

开发报告必须与实际工程状态一致。

不得声称完成了实际上没有修改、编译或测试的内容。

### 8.2 开发报告内容

至少包含：

1. 任务编号。
2. 任务目标。
3. 实际完成内容。
4. 修改文件清单。
5. 关键实现方式。
6. 重要代码或架构说明。
7. 编译结果。
8. 测试方法。
9. 测试结果。
10. 未解决问题。
11. 已知风险。
12. 与原任务要求的差异。
13. 后续建议。

### 8.3 文件状态确认

提交交付报告之前，模块开发 Agent 必须检查：

- 所有修改是否已经保存。
- 实际修改文件是否都在授权范围内。
- 是否意外修改其他文件。
- 是否存在未提交的修改。
- 是否存在无法确认状态的文件。

如果发现超出授权范围的修改，必须明确报告，不得隐瞒。

### 8.4 主程接收后的处理

主程 Agent 收到开发成果和交付报告后，执行以下判断：

**第一步：判断是否需要独立代码审核**

以下情况通常需要触发独立代码审核：

- 涉及 UE5 工程文件修改的开发任务。
- 涉及 C++ 代码编写或修改的任务。
- 涉及蓝图修改的任务。
- 主程评估后认为代码变更有足够复杂度或风险的任务。

以下情况可以不触发（由主程决定）：

- 仅修改项目 Markdown 管理文件。
- 仅维护技术文档。
- 代码变更极小且风险极低的修复任务。

**第二步：触发代码审核时**

主程将任务单、交付报告、工程访问权和相关技术文档交给代码审核 Agent（详见 3.4 开发成果至代码审核交接）。

在代码审核完成之前，原任务的文件锁定必须按照 File_Management_Rules.md 继续保留。

**第三步：不触发代码审核时**

主程直接进入最终技术验收。验收内容包括：

- 是否符合任务单要求。
- 是否超出授权文件范围。
- 是否影响现有系统。
- 是否存在明显代码问题。
- 是否通过要求的编译和测试。
- 是否存在未解决的关键问题。

### 8.5 交付报告冻结

正式提交的交付报告应视为一次交接记录。

如果后续发现报告存在错误，应通过补充说明或新版本报告修正。

不得无记录地覆盖已经提交的原始交付报告。

## 9. 主程最终技术验收交接规范

主程 Agent 完成最终技术验收后，应向总控 Agent 提交验收结果。

本交接是主程与总控之间的项目管理层交接，区分于代码审核 Agent 与主程之间的独立代码审核交接。

### 9.1 前置条件

主程进行最终技术验收前，必须完成以下前置步骤：

- 已收到模块开发 Agent 的完整交付报告。
- 如果触发了独立代码审核：已收到代码审核 Agent 的审核报告，并已处理完毕（审核结论为 Approved 或 Approved with Warnings，或主程已确认返工后的重新审核通过）。
- 如果未触发独立代码审核：主程已直接检查工程文件。

### 9.2 主程处理代码审核报告后的内部决策

主程收到代码审核报告后，在向总控交接前，内部完成以下判断：

- 审核结论为 Approved：通过。
- 审核结论为 Approved with Warnings：主程评估警告是否影响最终验收标准，决定接受或要求返工。
- 审核结论为 Changes Requested：主程整理返工清单，退回模块开发 Agent。此阶段不向总控交接，继续等待返工完成。
- 审核结论为 Rejected：主程重新评估方案，决定重做方向或取消任务。

### 9.3 最终技术验收交接内容

主程向总控提交的最终技术验收报告至少包含：

- 关联任务编号。
- 开发 Agent。
- 是否触发独立代码审核（是/否）。
- 代码审核结论（如触发）。
- 主程处理审核报告的结果（如触发）。
- 主程最终技术验收结论。
- 实际修改文件。
- 编译与测试结果。
- 遗留问题（如有）。
- 文件锁已释放（是/否）。
- 是否建议总控更新项目进度。

### 9.4 主程最终技术验收结论

主程最终技术验收结论分为：

- 通过：任务技术上可以接受。
- 有条件通过：可以接受但需要记录遗留问题。
- 不通过：必须返工后重新审核和验收。

### 9.5 总控后续动作

总控 Agent 根据主程的最终技术验收结果：

- 更新任务状态。
- 更新 Current_Status.md 中的项目进度。
- 对于重大功能、核心系统或重要里程碑，向人类管理者提交验收摘要。
- 根据人类管理者的意见决定是否正式接受。

## 10. Agent 更换与任务接手

### 10.1 适用情况

以下情况需要执行 Agent 更换交接：

- 原 Agent 无法继续工作。
- 原对话上下文丢失或过长。
- 需要切换 AI 平台。
- 需要切换模型。
- 原 Agent 的能力不适合继续执行。
- 人类管理者决定更换执行者。

### 10.2 原 Agent 的交接责任

原 Agent 应尽可能提供：

- 原始任务单。
- 已完成工作。
- 尚未完成工作。
- 当前工程文件状态。
- 已修改文件清单。
- 已知问题。
- 相关技术决策。
- 文件锁定情况。
- 下一步建议。

如果原 Agent 已无法使用，应由主程 Agent 检查真实工程状态并重新整理交接资料。

### 10.3 新 Agent 的接手流程

新 Agent 必须：

1. 阅读 Studio_Guide.md。
2. 阅读 Terminology.md。
3. 阅读 Agent_Permissions.md。
4. 阅读与当前任务有关的其他工作室规则。
5. 阅读原始任务单。
6. 阅读最新交接报告。
7. 检查当前工程状态。
8. 确认文件锁定情况。
9. 向主程 Agent 确认接手权限。
10. 获得确认后继续执行。

### 10.4 文件锁定继承

Agent 更换不会自动释放原任务的文件锁。

新 Agent 接手时，应继承原任务的授权文件范围和锁定关系。

主程 Agent 必须更新 File_Lock_Register.md 中的执行者信息。

### 10.5 不得擅自重新开始

新 Agent 不得仅凭自己的理解直接重写原有成果。

必须先检查：

- 已经完成的代码。
- 已经保存的文件。
- 原任务的技术决策。
- 已经通过的审核内容。

除非发现明确问题并获得相应授权，否则应在已有成果基础上继续工作。

## 11. 跨平台与跨模型交接

### 11.1 平台独立原则

AI Game Studio 不依赖某个特定 AI 平台。

所有核心项目资料都应保存在可访问的正式文件中。

更换平台时，不应导致工作室架构、任务编号和项目状态发生变化。

### 11.2 交接资料包

跨平台交接时，至少应提供：

**工作室规则：**

- Studio_Guide.md
- Terminology.md
- Agent_Permissions.md
- 与当前工作有关的其他固定规则。

**项目资料：**

- Project_Overview.md
- Current_Status.md
- 相关策划文档。
- 相关技术文档。

**任务资料：**

- 当前任务单。
- 最新交接报告。
- 文件锁定记录。
- 已有开发成果。
- 相关审核报告。

不需要每次都发送整个工作室和项目的全部文件。

应根据接收方的职责和当前任务，只提供必要资料。

### 11.3 新平台启动要求

新平台上的 Agent 必须先阅读交接资料，再开展工作。

如果新平台无法访问某些文件，必须明确说明缺失内容。

不得假装已经读取自己无法访问的文件。

### 11.4 模型能力差异

不同模型可能在代码能力、上下文长度、工具访问和文件操作能力方面存在差异。

接收方应根据自身实际能力执行任务。

如果发现无法完成原任务，应向主程 Agent 报告并提出替代方案。

不得因为模型能力不足而擅自降低验收标准。

## 12. 交接确认机制

### 12.1 交接发起

交接方完成必要资料整理后，将交接报告交给接收方。

### 12.2 接收方检查

接收方必须检查：

- 交接资料是否完整。
- 任务目标是否明确。
- 文件路径是否有效。
- 当前权限是否明确。
- 文件锁定状态是否明确。
- 是否存在影响继续工作的重大问题。

### 12.3 接受交接

接收方确认能够继续执行后，将交接状态标记为 Accepted。

如果交接内容不完整，应标记为 Rejected 或保持 Pending，并说明需要补充的信息。

### 12.4 交接完成

只有在以下条件满足后，才能将交接状态标记为 Completed：

- 接收方已经确认接受。
- 相关正式文件已经更新。
- 任务负责人和执行者信息已经更新。
- 必要的文件锁定记录已经同步。
- 交接双方的责任边界已经明确。

对于正常的成果提交，接收方确认收到并完成必要检查后，才算完成交接。

## 13. 交接与项目状态同步

所有重要交接必须及时同步到对应项目文件。

总控 Agent 负责维护：

- Current_Status.md
- Agent_Activity_Log.md
- 必要的 Project_Change_Log.md

主程 Agent 负责维护：

- Task_Backlog.md
- 任务单。
- File_Lock_Register.md。
- 技术审核记录。

交接双方应及时提交状态变化信息。

任何 Agent 不得直接修改不属于自己维护范围的权威文件。

---

## 14. 交接异常处理

如果发生以下情况，必须暂停后续工作并报告：

- 交接资料缺失。
- 交接报告与实际工程状态不一致。
- 接收方没有相应权限。
- 文件锁定记录无法确认。
- 任务单和交接报告存在冲突。
- 原 Agent 的修改内容无法追溯。
- 新平台无法读取必要文件。
- 接收方无法理解关键技术决策。

异常报告必须包含：

1. 关联任务编号。
2. 交接编号。
3. 具体异常。
4. 受影响文件。
5. 当前任务状态。
6. 已完成检查。
7. 建议解决方案。
8. 需要谁作出决定。

不得在交接状态不明确时擅自继续修改工程文件。

---

## 15. 交接规范优先级

交接工作按照以下顺序执行：

1. 人类管理者最新的明确指令。
2. 经人类管理者确认的工作室固定规则。
3. Agent_Permissions.md 中的权限规定。
4. File_Management_Rules.md 中的文件管理规定。
5. Task_Management_Rules.md 中的任务管理规定。
6. 本文件中的交接规范。
7. 当前项目的具体交接约定。

交接不得突破工作室固定规则和 Agent 权限。

如果规则之间出现冲突，必须暂停相关操作并请求确认。
