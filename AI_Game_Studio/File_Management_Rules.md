# AI Game Studio 文件管理规范

**文件名称：** File_Management_Rules.md

**工作室名称：** AI Game Studio

**当前版本：** 1.0

**文件性质：** 工作室核心固定规则

**适用范围：** 所有 Agent、所有游戏项目

**主要执行者：** 总控 Agent、主程 Agent

**最高管理者：** 人类管理者

---

## 1. 文件目的

本文件用于建立 AI Game Studio 统一的文件管理机制。

随着游戏项目规模扩大，多个 Agent 可能同时参与策划、技术设计、代码开发、测试和文档维护。

如果缺少统一的文件管理规则，可能出现：

- 多个 Agent 同时修改同一个文件。
- 一个 Agent 覆盖另一个 Agent 尚未保存的成果。
- 开发 Agent 修改了未经授权的工程文件。
- 不同任务之间发生文件冲突。
- Agent 更换后无法确定文件当前由谁负责。
- 任务中断后文件处于不明确状态。
- 项目文档与实际工程状态不一致。

因此，所有 Agent 必须遵循本文件规定的文件管理流程。

本文件重点规定：

1. 文件分类与目录管理。
2. 文件创建和命名。
3. 文件读取与修改。
4. 任务级文件锁定。
5. 文件冲突检测。
6. 文件锁定申请与释放。
7. 任务中断和 Agent 更换。
8. 文件版本与历史记录。
9. 文件保存和同步检查。

## 2. 文件管理基本原则

### 2.1 统一目录原则

每个游戏项目必须拥有独立的 AI 项目管理目录。

默认目录为：

```
游戏工程根目录/
└── AI_Project/
    ├── Project_Overview.md
    ├── Current_Status.md
    ├── Designer/
    ├── Technical/
    ├── Development/
    ├── Handoffs/
    ├── Reviews/
    └── Logs/
```

AI_Project/ 仅用于存储 AI 工作室产生的项目管理资料。

不得为了 AI 工作室的文件管理需求，随意改变 UE5 工程原有目录结构。

### 2.2 职责归属原则

每个正式文件都必须有明确的维护责任人。

默认维护关系：

- **Project_Overview.md：** 总控 Agent
- **Current_Status.md：** 总控 Agent
- **Designer/：** 游戏策划 Agent
- **Technical/：** 主程 Agent
- **Development/：** 主程 Agent
- **Handoffs/：** 交接双方
- **Reviews/Design_Reviews/：** 对应设计审核者
- **Reviews/Code_Reviews/：** 代码审核 Agent
- **Reviews/Test_Reports/：** 对应测试执行者及审核者
- **Logs/：** 总控 Agent

维护者负责文件内容的日常更新，但不代表其他 Agent 完全不能读取该文件。

其他 Agent 是否可以修改文件，必须依据 Agent_Permissions.md 判断。

### 2.3 单一写入原则

同一时间，同一个文件只能由一个有效任务或一个获得明确授权的维护者进行修改。

禁止多个 Agent 同时对同一个文件进行独立写入。

### 2.4 修改前读取原则

任何 Agent 在修改文件之前，都必须先读取文件的最新版本。

不得仅凭之前的聊天记录、旧版本内容或记忆直接覆盖文件。

### 2.5 修改后检查原则

任何 Agent 完成文件修改后，必须检查：

- 文件是否成功保存。
- 修改内容是否完整。
- 是否误删其他内容。
- 是否产生格式错误。
- 是否影响其他文档中的引用。
- 是否需要同步更新关联文件。

如果无法确认保存成功，必须明确报告，不能声称已经完成同步。

## 3. 文件分类与管理

### 3.1 工作室固定规则文件

工作室固定规则统一存放在 Studio_Core/ 目录下。

例如：

```
AI_Game_Studio/
└── Studio_Core/
    ├── Studio_Guide.md
    ├── Terminology.md
    ├── Agent_Permissions.md
    ├── File_Management_Rules.md
    ├── Task_Management_Rules.md
    └── Handoff_Rules.md
```

这些文件可以被所有 Agent 按权限读取。

任何 Agent 不得擅自修改固定规则。

总控 Agent 可以提出修改建议，只有经过人类管理者明确确认后，才能执行规则修改。

Terminology.md 的新术语登记按照 Agent_Permissions.md 中的特殊授权规则执行。

### 3.2 游戏项目动态文件

游戏项目动态文件存放在各自工程的 AI_Project/ 目录下。

这些文件会随着项目开发不断创建和更新。

各 Agent 必须根据职责维护对应目录，不得随意修改其他 Agent 负责的文件。

### 3.3 UE5 工程文件

UE5 工程本体包括：

- Source/
- Content/
- Config/
- Plugins/
- 项目配置文件。
- 其他实际工程资源。

这些文件不是普通的项目管理文档。

工程文件必须按照主程 Agent 创建的开发任务单进行授权和管理。

模块开发 Agent 只能修改任务单中明确列出的文件。

## 4. 文件命名规范

### 4.1 基本要求

所有正式文件应使用能够表达内容的名称。

优先采用英文单词和下划线组合，避免使用含义模糊的名称。

例如：

正确：

- Project_Overview.md
- Game_Design.md
- Technical_Architecture.md
- Task_Backlog.md
- File_Lock_Register.md
- Code_Review_Report.md

不推荐：

- 文档1.md
- 新文件.md
- 最终版.md
- 最终版2.md
- 临时文件最新版.md

### 4.2 任务文件命名

任务文件应包含任务编号和简短任务名称。

推荐格式：

```
Task_001_Player_Movement.md
Task_002_Interaction_System.md
Task_003_Inventory_System.md
```

任务编号必须唯一，不得因为任务取消或归档而重新分配给其他任务。

### 4.3 交付文件命名

推荐格式：

```
Task_001_Developer_Report.md
Task_001_Technical_Review.md
Task_001_Test_Report.md
```

### 4.4 文件命名变更

正式文件一旦被其他文档引用，不得随意重命名。

如果确实需要重命名，必须同步检查所有引用该文件的文档，并更新相关路径。

## 5. 文件读取与修改流程

### 5.1 修改前检查

Agent 修改文件之前必须完成以下检查：

1. 确认自己拥有该文件的修改权限。
2. 确认文件属于当前职责或任务范围。
3. 读取文件最新版本。
4. 检查文件是否已被其他任务锁定。
5. 检查本次修改是否会影响其他文件。
6. 确认修改内容符合项目现有规范。

任何一项无法确认时，都必须暂停修改。

### 5.2 修改过程

修改过程中必须：

- 尽量保留文件中已有的有效内容。
- 不得无理由重写整份文件。
- 不得删除其他 Agent 已经提交的有效成果。
- 不得擅自改变已批准的设计或技术决策。
- 如果发现原文件存在问题，应先记录并说明原因。
- 如果需要扩大修改范围，必须先获得相应授权。

### 5.3 修改完成

修改完成后必须：

1. 检查文件内容。
2. 检查文件格式。
3. 检查相关引用。
4. 检查是否需要更新其他关联文件。
5. 确认保存结果。
6. 在任务报告或工作记录中说明修改内容。

## 6. 任务级文件锁定机制

### 6.1 锁定机制定义

AI Game Studio 采用任务级文件锁定机制。

所谓任务级文件锁定，是指：

一个开发任务所涉及的全部工程文件，在任务开始执行后，由该任务独占，直到任务通过审核或被正式终止。

同一个文件不得同时分配给两个正在执行的任务。

文件锁定的目的不是限制正常读取，而是防止多个 Agent 同时修改同一个文件。

### 6.2 文件锁定管理者

主程 Agent 是工程文件锁定的唯一管理者。

主程 Agent 负责：

- 检查文件是否已被锁定。
- 创建任务时确定需要锁定的文件。
- 更新 File_Lock_Register.md。
- 审批任务中的新增文件申请。
- 审核任务完成情况。
- 释放已经结束的任务所持有的文件锁。
- 处理任务中断和文件冲突。

总控 Agent 可以检查和监督锁定记录，但不得擅自修改锁定状态。

### 6.3 文件锁定前检查

主程 Agent 创建任务之前，必须检查：

1. 当前任务需要修改哪些文件。
2. 这些文件是否真实存在。
3. 是否存在其他任务已经锁定这些文件。
4. 是否存在尚未结束的关联任务。
5. 是否需要与其他任务协调执行顺序。
6. 是否需要拆分任务以降低文件冲突风险。

如果发现文件已被其他任务锁定，不得直接分配新任务。

主程 Agent 应选择：

- 等待现有任务完成。
- 调整任务执行顺序。
- 将任务拆分为不冲突的子任务。
- 在必要时重新设计任务边界。

### 6.4 文件锁定生效

只有同时满足以下条件，任务才能正式开始修改工程文件：

- 任务单已经创建。
- 任务授权的文件清单已经明确。
- 所有文件均通过冲突检查。
- File_Lock_Register.md 已更新。
- 当前任务已经获得执行授权。

文件锁定记录必须先于实际修改生效。

不得先修改文件，再补写锁定记录。

### 6.5 锁定期间的限制

文件被任务锁定后：

- 其他任务不得修改该文件。
- 其他模块开发 Agent 不得接管该文件。
- 策划 Agent 不得直接修改该文件。
- 总控 Agent 不得擅自修改该文件。
- 主程 Agent 不得将该文件重新分配给其他任务。

如果主程 Agent 需要亲自修改该文件，也必须先结束或正式接管原任务，避免出现两个独立修改者。

读取文件不受锁定限制，但读取者不得将读取权限理解为修改权限。

### 6.6 任务文件范围

任务单必须明确列出允许修改的文件。

推荐格式：

```
## 允许修改的文件

- Source/DualLink/Player/PlayerCharacter.cpp
- Source/DualLink/Player/PlayerCharacter.h
- Source/DualLink/Components/MovementComponent.cpp

## 禁止修改的文件

- Source/DualLink/GameMode/GameModeBase.cpp
- Config/DefaultEngine.ini
- 其他未授权文件
```

允许修改的文件清单是任务授权的边界。

未列出的文件默认不允许修改。

### 6.7 新增文件申请

开发过程中，如果 Agent 发现必须修改原任务文件清单之外的文件：

1. 暂停对新增文件的修改。
2. 向主程 Agent 提交申请。
3. 说明新增文件的路径。
4. 说明修改原因。
5. 说明可能影响的其他模块。
6. 主程检查新增文件是否存在锁定冲突。
7. 主程批准后更新任务单。
8. 主程更新文件锁定记录。
9. 开发 Agent 获得更新后的任务授权后继续工作。

未经批准，不得擅自扩大任务范围。

## 7. File_Lock_Register.md 文件锁定登记表

每个游戏项目必须维护一份文件锁定登记表：

```
AI_Project/
└── Development/
    └── File_Lock_Register.md
```

该文件由主程 Agent 唯一维护。

### 7.1 登记表内容

文件锁定登记表至少应包含：

- 任务编号。
- 任务名称。
- 当前执行者。
- 被锁定文件。
- 锁定时间。
- 当前任务状态。
- 预计结束时间（如果能够确定）。
- 最后更新时间。
- 备注。

### 7.2 登记表模板

```
# 文件锁定登记表

## 当前有效锁定

- **任务编号：** Task_001 — **任务名称：** 玩家移动系统 — **执行者：** Module Developer A — **锁定文件：** PlayerCharacter.cpp — **锁定时间：** 2026-11-09 — **任务状态：** In Progress

## 已释放锁定

- **任务编号：** Task_000 — **任务名称：** 初始化系统 — **原执行者：** Module Developer B — **释放时间：** 2026-11-08 — **释放原因：** 审核通过

## 异常锁定记录

- **任务编号：** — **异常情况：** — **当前处理状态：** — **备注：**
```

以上日期和任务仅为格式示例，实际项目中必须填写真实信息。

### 7.3 锁定状态

文件锁定状态至少包含：

- Locked：已锁定。
- Released：已释放。
- Suspended：任务暂停，锁定继续保留。
- Pending：等待主程批准或处理。

不得将暂停任务的锁定状态误认为已释放。

## 8. 文件锁定释放机制

### 8.1 正常释放

开发任务的文件锁定释放是整个开发流程的最后一步。

释放前必须完成：模块开发提交 → 独立代码审核（如触发）→ 主程处理审核报告 → 主程最终技术验收。

只有在以下条件全部满足时，主程 Agent 才能释放文件锁：

1. 开发 Agent 已提交完整交付报告。
2. 独立代码审核 Agent 已完成审核（如主程判断需要代码审核）。
3. 主程已处理完毕代码审核报告（如涉及）。
4. 主程已完成最终技术验收。
5. 不存在尚未解决的 Critical 或 High 级别问题。
6. 主程已更新 File_Lock_Register.md。

完成上述流程后，主程才能将文件状态改为 Released。

### 8.2 审核未通过与返工

以下情况文件锁定均继续保留，不得释放给其他任务：

**独立代码审核未通过**

- 代码审核 Agent 出具 Changes Requested 或 Rejected 报告。
- 原任务的文件锁定继续保留。
- 主程根据审核报告整理返工清单。

**返工期间**

- 开发 Agent（原开发者或新接手者）在原任务授权范围内返工。
- 文件锁定继续保留，锁定范围不变。
- 如果更换开发者，主程更新 File_Lock_Register.md 中的执行者信息，但不释放锁定。

**重新审核期间**

- 返工完成后，主程将新成果交给代码审核 Agent 重新审核。
- 重新审核期间文件锁定继续保留。
- 无论重新审核结果如何，锁定都保持到主程完成最终技术验收。

以上三个阶段中，文件锁定状态均保持 Locked 或 Suspended，不得提前释放。

### 8.3 任务正式取消

如果任务被正式取消：

1. 主程检查当前工程文件状态。
2. 确认已经完成的修改是否保留。
3. 确认是否需要恢复到任务开始前的版本。
4. 记录未完成内容和潜在风险。
5. 更新任务状态。
6. 释放文件锁。
7. 将任务和交付记录归档。

取消任务不意味着必须撤销所有已经完成的修改。

### 8.4 禁止提前释放

以下情况不得释放文件锁：

- 开发 Agent 尚未提交成果。
- 独立代码审核尚未完成（如果已触发）。
- 代码审核结论为 Changes Requested 或 Rejected，返工尚未完成。
- 返工完成后重新审核尚未完成。
- 主程最终技术验收尚未完成。
- 任务只是暂时暂停。
- Agent 暂时无法联系。
- Agent 更换但尚未完成正式交接。
- 文件当前状态不明确。

## 9. 任务中断与 Agent 更换

### 9.1 任务中断

如果开发任务由于平台异常、对话中断、Agent 无法继续工作等原因停止：

- 保留原任务编号。
- 保留原文件锁定记录。
- 记录最后完成的工作。
- 记录尚未完成的工作。
- 记录当前文件修改状态。
- 记录已知问题和风险。

任务中断不代表任务结束。

### 9.2 Agent 更换

如果需要更换执行任务的模块开发 Agent：

1. 原 Agent 提交当前工作报告。
2. 主程检查当前文件状态。
3. 主程确认原任务是否需要继续。
4. 将原任务授权和文件清单交给新 Agent。
5. 更新文件锁定登记表中的执行者。
6. 新 Agent 阅读已有任务记录和交接报告。
7. 新 Agent 确认当前文件状态后继续工作。

Agent 更换时，不得释放原任务的文件锁再重新申请。

### 9.3 无法确认文件状态

如果任务中断后无法确认文件是否已经被修改：

- 暂时保留文件锁定。
- 不允许其他任务修改相关文件。
- 主程必须检查工程实际状态。
- 必要时通过版本管理工具检查修改差异。
- 确认文件状态后才能恢复任务或释放锁定。

## 10. 文件版本与历史管理

### 10.1 基本原则

重要项目文件的修改必须能够追溯。

不得随意覆盖重要文件而不保留必要的历史信息。

### 10.2 Markdown 文件历史

对于重要的策划、技术、任务和审核文件，应通过以下方式之一保留历史：

- Git 版本管理。
- 文档版本记录。
- 变更日志。
- 历史版本归档。

具体方式由项目实际工具环境决定。

### 10.3 工程文件历史

UE5 工程代码和资源建议使用 Git 等版本管理工具。

正式开发任务开始前，应确认当前工程状态。

开发任务结束后，应能够检查任务涉及的文件修改差异。

### 10.4 禁止覆盖历史成果

不得直接覆盖仍然具有参考价值的旧版策划方案、技术决策或任务交付报告。

如果需要修改已经完成的文档，应尽量保留历史记录。

## 11. 文件同步与保存规范

### 11.1 实时保存原则

Agent 完成一项具有长期价值的工作后，应立即更新对应的项目 Markdown 文件。

不得长期只把重要成果保存在聊天记录中。

### 11.2 修改前同步

修改文件前，必须读取本地或当前工作区中的最新版本。

如果聊天记录与文件内容不一致，以实际文件中的最新有效版本为准。

### 11.3 修改后同步

修改完成后，必须检查：

- 文件是否成功写入。
- 内容是否完整。
- 是否存在格式错误。
- 是否需要更新关联文档。
- 是否需要更新任务状态。

### 11.4 无法保存时

如果当前 Agent 无法访问文件系统或无法保存文件：

必须明确报告：

- 哪个文件无法访问。
- 原因是什么。
- 当前成果是否只保存在聊天记录中。
- 需要人类管理者执行什么操作。

不得声称文件已经更新。

### 11.5 权威文件维护

以下文件必须由指定 Agent 维护：

- **Current_Status.md：** 总控 Agent
- **File_Lock_Register.md：** 主程 Agent
- **Project_Overview.md：** 总控 Agent
- **Task_Backlog.md：** 主程 Agent

其他 Agent 可以提交更新建议或状态信息，但不能直接修改这些文件。

---

## 12. 文件冲突处理

如果发现文件已经被其他任务锁定，或者发现多个 Agent 对同一个文件产生了修改冲突，必须立即停止进一步写入。

处理流程：

1. 确认发生冲突的文件。
2. 确认相关任务编号。
3. 确认当前文件的实际状态。
4. 检查各任务的修改记录。
5. 由主程 Agent 判断冲突范围。
6. 必要时请求总控 Agent 协调。
7. 确定保留、合并或撤销哪些修改。
8. 更新相关任务单和文件锁定记录。
9. 确认文件恢复到一致状态后，才能继续开发。

任何 Agent 不得自行覆盖其他任务的修改来解决冲突。

## 13. 物理文件管理与协作协议的区别

本文件定义的是 AI Game Studio 的文件管理协议。

必须明确：

**文件锁定记录不等于操作系统层面的物理文件锁。**

如果多个 Agent 使用同一个具有完整写入权限的工作区，仅依靠 Markdown 中的锁定记录，无法从技术上完全阻止误修改。

因此，具备相应条件时，应优先使用以下措施：

- Git 分支隔离。
- 独立工作区。
- 任务结束后的代码差异检查。
- 重要文件备份。
- 合并前审核。
- 人工检查关键修改。

如果当前平台不支持这些功能，所有 Agent 仍必须遵守本文件规定的逻辑锁定机制。

不得将逻辑锁定描述成已经实现的系统级强制保护。

## 14. 文件管理异常报告

遇到以下情况时，Agent 必须及时向主程或总控报告：

- 发现未经授权的文件修改。
- 发现文件锁定记录与实际工程状态不一致。
- 发现文件丢失或内容损坏。
- 发现两个任务同时修改同一文件。
- 发现重要文档被意外覆盖。
- 发现任务交接后文件状态不明确。
- 发现当前 Agent 无法保存或读取必要文件。

异常报告必须包含：

1. 异常文件路径。
2. 相关任务编号。
3. 发生的问题。
4. 已知原因。
5. 当前影响。
6. 已采取的措施。
7. 建议的后续处理方式。

## 15. 文件管理规范优先级

文件管理相关规则按照以下顺序执行：

1. 人类管理者最新的明确指令。
2. 经人类管理者确认的工作室固定规则。
3. Agent_Permissions.md 中的权限规定。
4. 本文件中的文件管理规范。
5. 当前项目的文件管理约定。
6. 当前任务单中的具体执行要求。

任务单不得突破工作室固定规则和 Agent 权限。

如果不同规则之间出现冲突，必须暂停相关操作并请求确认。
